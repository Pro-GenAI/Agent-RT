CircleCI configuration lives at `.circleci/config.yml` and is intentionally Apple Silicon macOS (`arm64`) only, with one exception: the `python_raspberry_pi` and `typescript_raspberry_pi` jobs (`run_pi_ci` parameter, `raspberry_pi_ci` workflow) run on the Linux `arm.large` machine executor because macOS executors have no Docker. They run the Python 3.12 / Node 22 suites plus the deterministic offline security gates (Python `security_scan.py` and `security_attack_scan.py`, TypeScript `npm run security:gate`) natively on arm64 in Docker capped like a Raspberry Pi 4/5 (`--cpus=4 --memory=4g --memory-swap=4g`, set once in the executor's `PI_DOCKER_LIMITS`) and must keep asserting `aarch64` and the 4 GiB cgroup limit. Everything else stays on macOS, unlike ordinary local tests and GitHub cross-platform CI, which can run on Linux, Windows, or Intel (`x86_64`) macOS. Passing tests on Intel macOS does not establish CircleCI compatibility: investigate Apple Silicon-specific dependencies, optional native Node modules, architecture-specific binaries, and security-tool behavior before declaring a CircleCI failure resolved. Keep every other CircleCI job on the `m4pro.medium` macOS resource class (or a documented successor Apple-silicon class), preserve an explicit `arm64` architecture assertion, run the supported Python and Node regression matrices plus the Python `make test-browsers` web UI job (browser tests run only on CircleCI, never in GitHub CI), and keep the repository security gates deterministic/offline with respect to real LLM/model endpoints.
