# Migration test maintenance guide

This directory contains the field-test runner used to measure compatibility of the documented Agent RT migration against third-party repositories. Treat every tested repository and every command it supplies as untrusted input.

## Keep documentation current

After changing migration-test behavior, setup heuristics, supported migration surfaces, output/status semantics, provider mocks, dependencies, CLI behavior, concurrency, isolation, or cleanup, update this `AGENTS.md` and the relevant user-facing parts of `README.md` in the same change. Keep implementation details here; keep `README.md` focused on purpose, safety, result shape, and normal usage.

## Important files

- `migration_test.py`: orchestration, repository setup, test execution, migration rewriting, retries, concurrency, result persistence, and cleanup.
- `heavy_package_audit.py`: heavyweight/local-ML dependency detection used to filter repositories before installation.
- `mock_server.mjs`: compatibility routes layered on top of the provider mock server.
- `repo_list.csv`: migration-test input repositories. Its `Package` values must be keys of `PYTHON_IMPORT_ROOTS` (and of `TS_SPECIFIER_RULES` for TS/JS rows); `load_targets` fails fast otherwise, because an unknown name silently records every row of that group as `NO_CHANGES`/`UNSUPPORTED`.
- `test_migration_runner.py`: offline stdlib `unittest` regressions for runner heuristics (`python -m unittest test_migration_runner`). Whenever a field run exposes a new setup/baseline failure that the runner can fix, add a test reproducing it there (name the repository in the docstring) in the same change.
- `migration_results.csv`: resumable result database, maintained as CSV.
- `summarize_migration_results.py`: read-only report of PASS/PASS, baseline-PASS, and total row counts per package and language; update it if result columns or status names change.
- `Migration-Test-Targets.md`: target/framework coverage information.
- `pyproject.toml`, `uv.lock`, `.python-version`: Python tooling/runtime definition.
- `package.json`, `package-lock.json`: Node dependency definition for provider mocking.

## Core runner invariants

- Keep the runner disposable and resumable.
- Each worker process handles exactly one untrusted repository at a time.
- Concurrent workers use isolated checkout and uv/npm/yarn/pnpm cache paths.
- Only the parent process writes the shared `migration_results.csv`.
- Strip likely credential environment variables before running third-party setup or tests.
- Record the exact tested commit and both before/after results.
- Delete each repository checkout and its package caches in a `finally` path so disk use stays bounded and workers never race on shared caches. Every cache and temp location tools may write to is redirected under the repository's `.cache-NNNN` directory (`process_target`): uv, npm, yarn (classic and Berry global), pnpm store, bun, corepack, pip, `XDG_CACHE_HOME`, Puppeteer/Playwright/Cypress/Electron browser downloads, Hugging Face, and `TMPDIR`/`TMP`/`TEMP`. Anything written to the user's `~/.cache` or `/tmp` instead accumulates across hundreds of repositories (dependency install scripts now run and download browsers) until the disk fills.
- Each work root records its owner PID (`.owner-pid`); at startup, before writing any log, `remove_stale_work_roots` deletes `agent-rt-migration-*` directories whose owner is dead (or, without an owner file, older than a day), so runs killed by SIGKILL or a reboot do not leak disk. SIGTERM is turned into `KeyboardInterrupt` so `finally` cleanup runs.
- `--min-free-gb` (default 10) is checked under the temp and log directories at startup and before each repository starts (parallel runs submit at most `--workers` repositories at a time for this). Below it, the run stops cleanly with exit code 1, keeping the `--resume` progress file.
- Do not weaken the expectation that this tooling runs inside an OS/container/VM sandbox with an explicit network policy appropriate for untrusted code.

## Result and resume semantics

`migration_results.csv` is one row per normalized repository URL. URL matching is case-insensitive and ignores a trailing slash or `.git`. At startup, duplicate URLs already in the CSV are collapsed to the latest row. Normal runs skip URLs already present, and newly completed work replaces the existing row for that URL instead of keying identity on index, package, or language metadata.

`--retry-failed` reruns only URLs whose before/after status is retryable, including `FAIL`, `SETUP_FAILED`, `CLONE_FAILED`, `AGENT_RT_INSTALL_FAILED`, and `RUNNER_ERROR`, then replaces the existing row. At startup the runner renumbers `Index`, `Package`, `Language`, and `PLIndex` of existing result rows from the current `repo_list.csv` (matched by URL, first occurrence wins), so numbering stays correct after rows are added to or removed from the list. `--indices 14,21,30-35` reruns exactly those current `repo_list.csv` indices, even if already completed, replacing their rows; use it to recheck rows affected by a runner change without a full `--restart`. `--pass-fail` reruns only rows whose status is `PASS / FAIL` (baseline passed, migrated suite failed), replacing them; every other row and every not-yet-run repository is skipped, `--start-index`/`--indices`/`--limit` narrow that set further, and it cannot be combined with `--restart`. Use it to recheck compatibility fixes. `--restart` truncates the results file first.

Explicit selections (`--indices`, `--pass-fail`, `--retry-failed`) are resumable. The parent records each finished repository URL in `migration_results.rerun-progress.json` (git-ignored, atomically replaced, written right after the CSV row) together with the selection flags. `--resume` skips URLs already finished by the same selection (a missing file just starts fresh); a different selection is refused rather than guessed. Without `--resume`, a selection run resets the file. It is deleted when the selection completes, and `--resume` cannot be combined with `--restart` or used on a normal run (normal runs already skip completed URLs).

The human-readable status fields include states such as `PASS`, `FAIL`, `SKIPPED`, `SETUP_FAILED`, `FILTERED_HEAVY`, and `NO_TESTS`. Detailed result fields are compact JSON containing exit code, duration, captured output, setup adjustments, and after migration the changed files/count where applicable. Heavyweight repositories are recorded as `FILTERED_HEAVY / SKIPPED`, including detected package names and manifest paths, without installing dependencies or running tests. If the baseline suite fails, record `FAIL / SKIPPED` and do not migrate or run the post-migration suite.

## Concurrency and logging

Repository processing uses the current process by default (`--workers 1`), so sequential runs do not create a worker process. `--workers N` with `N > 1` enables concurrent worker processes. Worker logs stream continuously and may interleave when concurrency is enabled. Log the current phase and command outcome/output without echoing full command lines on the console. Print a blank line and a 100-character dash separator when a repository finishes.

Every run also writes logs under `--log-dir` (default `./logs`, git-ignored): `run-<stamp>.log` mirrors the console for the whole run, and `<stamp>/<index>-<owner>_<repo>.log` holds one repository's output. `TeeStream` replaces `sys.stdout`/`sys.stderr` in the parent and, through the `ProcessPoolExecutor` initializer, in each worker, so every process owns its own line-buffered append handles. `log_only()` writes text to the log files but not the console; `run_command` uses it for the working directory, the full command line, and untruncated command output (the console and result JSON keep the `--max-output-chars` tail). Keep failure causes discoverable from the per-repository log alone.

Typical phases are clone, heavyweight-dependency audit, dependency setup, initial tests, migration rewrite, Agent RT install, tests after migration, and cleanup.

## Heavyweight dependency filtering

Run the audit before dependency installation. `heavy_package_audit.py` scans dependency manifests for heavyweight/local-ML stacks such as PyTorch, Transformers, sentence-transformers, TensorFlow/JAX, ONNX Runtime, vLLM, and similar packages. Repositories that match are filtered rather than installed or tested.

## Python repository setup

Python setup is uv-native. Create the disposable `.agent_rt_venv` with `uv venv --managed-python --seed` using `PYTHON_VERSION` (CPython 3.12). 3.12 ties 3.13 on the `requires-python` ranges declared across the target repositories and has wheels for far more of their older pinned dependencies. No single version satisfies every declared range (some repositories require `>=3.13`, others `<3.12`), so `select_python_version` falls back through `PYTHON_VERSION_ALTERNATIVES` (3.13, 3.11, 3.14, 3.10) only when a `requires-python` (or Poetry `python`) range excludes 3.12. The ranges considered are the root's and those of nested projects that own tests (`python_project_ranges`); nested examples/demos do not constrain the choice. `.python-version` files are ignored. Do not reintroduce failure-driven version retries: they made results depend on which version happened to work.

Interpreter isolation:

- `sanitized_env()` drops variables that point tools at the runner's own interpreter (`VIRTUAL_ENV`, `CONDA_*`, `PYTHONHOME`, `PYTHONPATH`, `UV_PYTHON`, `UV_PROJECT_ENVIRONMENT`, and similar), removes virtualenv/conda `bin` directories from `PATH` (the runner usually runs under `uv run` and often inside an activated conda env), and sets `UV_MANAGED_PYTHON=1` so uv never selects a conda or system interpreter.
- Setup commands and test runs execute with the repository venv activated (`VIRTUAL_ENV` set, venv `bin` first on `PATH`), so tests that spawn `python`, `pytest`, `pip`, or console scripts use `.agent_rt_venv`.
- `uv sync --frozen` receives `--python <venv python>`; without it uv may replace the venv with a different interpreter.
- Committed `*.egg-info` directories are deleted before setup. Once a project is editable-installed its source directory is on `sys.path`, so stale egg-info becomes a duplicate distribution (for example duplicate pytest entry points aborting with "Plugin already registered").
- Dependency manifests are decoded with BOM/UTF-16 detection (`read_manifest_text` in `heavy_package_audit.py`); Windows-generated UTF-16 `requirements.txt` files otherwise bypass the heavyweight audit and requirement heuristics.

- If the repository has a root `uv.lock`, run `uv sync --frozen` into that environment.
- Otherwise install root requirements when present, install declared `pyproject.toml` dependencies, and attempt editable installs for local Python projects in shallow monorepos.
- Ignore nested example/demo requirements unless their directory looks like a testable Python project.
- Treat a failed editable install for the root project, or for a nested project that owns tests, as a setup failure rather than silently ignoring it.
- Use `uv pip install` for pytest, editable project installs, and the local Agent RT package. The parent builds the Agent RT wheel once per run (`build_agent_rt_wheel`, `uv build --wheel` into the work root) and every worker installs that wheel; installing from `python/` made concurrent workers run setuptools builds in the shared source directory at once, which hung installs for the full command timeout. If the wheel build fails, workers fall back to the source directory.
- Always install `pytest-timeout` and run with `--timeout=120` per test (unless the repository configures its own timeout) so one hanging test fails alone instead of the whole suite hitting the command timeout.
- An editable install that fails only because `pyproject.toml` metadata is invalid (for example Poetry `^3.11` in PEP 621 `requires-python`, or a `build-backend` naming a module the backend package lacks, such as `setuptools.backends.legacy:build`) is skipped with a message instead of failing setup; sources remain importable through `PYTHONPATH`.
- Test runs set `UV_PROJECT_ENVIRONMENT` and `UV_PYTHON` to the repository venv so tests that shell out to `uv run`/`uv sync` reuse it instead of building another environment.
- `git clone` is retried up to `CLONE_ATTEMPTS` times for transient network failures (but not for a missing repository). Clones override any inherited Git LFS filter (`GIT_CLONE_LFS_OFF`, `GIT_LFS_SKIP_SMUDGE=1`): without the git-lfs binary the checkout otherwise aborts with `git-lfs: not found`, and LFS objects are never needed for tests.
- Treat projects with no `[build-system]`, or with `tool.uv.package = false`, as virtual projects and do not editable-install them. A nested virtual project that owns tests (`project_owns_tests`: a `tests/`/`test/` directory or `test_*.py`) still gets its `[project]` dependencies, optional extras, and test groups installed, because only the root's were otherwise installed (a `backend/` with `backend/tests/` failed on every import).
- Install PEP 735 `[dependency-groups]` dev/test groups. Install every `[project.optional-dependencies]` extra first (test suites often import optional integrations), falling back to only dev/test extras if that fails. For `uv.lock` repositories run `uv sync --frozen --all-extras`, falling back to the default sync.
- When there is no root requirements file, use the cookiecutter-style `requirements/` directory, preferring `test`, `tests`, `testing`, `dev`, `development`, `local`, then `base` `.txt`.
- Source-only distributions in `SOURCE_ONLY_REPLACEMENTS` (for example `psycopg2`, which needs `pg_config`) are proactively swapped for an unpinned binary drop-in in the `.agent_rt_relaxed-*` copy.
- Install up front only the pytest plugins that pytest configuration or async tests strictly need (`PYTEST_PLUGIN_HINTS`, for example `--ds=` → pytest-django, `pytest.mark.asyncio` → pytest-asyncio, `--cov` → pytest-cov, `-n auto` → pytest-xdist); without them pytest aborts at startup or every async test fails, so installing them cannot change a passing baseline.

Setup commands must clear inherited `PYTHONPATH` and enable Python safe-path mode so project files such as `types.py` cannot shadow stdlib modules during installation. Apply the broader test `PYTHONPATH` only while running tests. It may include the repository root, top-level non-package source directories, and the parent of shallow nested `tests/` directories containing Python modules or a non-package `src/` directory (tests importing `src.pkg.mod`). Never add a package directory (one with `__init__.py`): it is already importable from the root, and adding it exposes its submodules as top-level modules (for example `tools/httpx.py` shadowing the real `httpx`, which breaks `openai`). Exclude directories containing modules named like stdlib modules or the common third-party modules in `SHADOWABLE_THIRD_PARTY`.

Undeclared dependencies come only from the curated `COMMON_IMPORT_DEPENDENCIES` mapping (for example `redis`, `yaml`, `markdown`, `bs4`); never derive distribution names from arbitrary import names, and never install one for a module local to the repository. Keys may be dotted (`google.genai`) for namespace packages (`from google import genai` counts as `google.genai`), and the longest curated prefix wins. Install them up front (many are imported inside `try/except`, so no error ever names them) except for package families that test files skip-gate: if a test line mentioning `skip` names a curated module or distribution (`importorskip("autogen")`, `reason="langchain-core not installed"`), that whole family (`langchain*`) is left out, because installing it, even transitively, un-skips tests a passing baseline never ran. Install hints in error output (`requires the httpx2 package`, `pip install httpx2`) install only names listed in `HINTED_PACKAGES`. Fixture plugins (`PYTEST_FIXTURE_PLUGINS`) and anything still missing are installed only after a run reports them: `missing_dependencies_from_output` maps `No module named 'X'`, `cannot import name 'Y' from 'X' (unknown location)`, `fixture 'Z' not found`, and "async def functions are not natively supported" (pytest-asyncio plus `-o asyncio_mode=auto`), installs, and reruns.

When a requirements file fails to resolve, the runner may create a sibling `.agent_rt_relaxed-*` copy, remove packages that the resolver reports as absent from the registry, unpin requirements whose requested version does not exist or whose exact pins the resolver reports as mutually incompatible, and retry that relaxed copy (up to five rounds).


## Repository environment placeholders

Before the first test run (Python and Node), fill deterministic placeholders only for environment variables the repository cannot import or start without, so tests do not fail solely because a required setting is missing. Filling optional settings is harmful: it turns on code paths the suite expects to be off (webhook signature checks returning 401/403, live-provider tests, alternate model names, stricter validation), so earlier broad filling broke many passing suites.

A variable is required when it is read with `os.environ["X"]` (not assigned), django-environ / python-decouple calls without a default (`env("X")`, `env.db("X")`, `config("X")`), a secret-like or database-URL pydantic `BaseSettings` field without a default, or an optional read (`getenv`, `environ.get`, `process.env`) whose name appears in an error raised at module import (`raise`/`throw` outside any function, see `raised_at_import`). Errors raised inside functions are left alone because tests may assert them. Variables that a test file mentions on a line containing `skip` are excluded, because they gate live tests that should stay skipped.

Values: secret-like names (`SECRET_ENV_NAME`; token counts such as `MAX_TOKENS`, and flag/count/duration/path names matched by `NON_SECRET_ENV_NAME` such as `MAX_SESSIONS_PER_API_KEY`, `CACHE_API_KEY_ENABLED`, `CACHE_API_KEY_TTL_SECONDS`, `AUTH_DISABLE_USERNAME_PASSWORD`, `PRIVATE_KEY_PATH` are not secrets) get the 64-hex-character `PLACEHOLDER_SECRET` (long enough for `min_length=32` validators and a valid 256-bit hex key), and a `<PREFIX>_API_KEY` also points `<PREFIX>_BASE_URL`/`<PREFIX>_API_BASE` at the mock. Python database URLs get a local SQLite file, as `sqlite+aiosqlite:///` (with `aiosqlite` installed after setup) when the repository uses SQLAlchemy's asyncio extension (never for Node, where ORMs such as Prisma validate the scheme). `*MODEL*` names that are really provider/adapter enums or paths are not given a model name. Token counts get an integer, `*MODEL*` names a mock-served model, and other names a non-network `.env.example` value or nothing. Do not synthesize other URL or host settings, except Celery's server-less in-memory transport (`NON_NETWORK_URL_PLACEHOLDERS`, any `*_BROKER_URL` → `memory://`, `CELERY_RESULT_BACKEND` → `cache+memory://`), which settings modules commonly require at import. Never print the names on the console; they go to the log files and to `setup_adjustments`.

## Baseline-test setup retries

If initial tests fail, the runner retries harness-level problems, reusing the adjusted pytest command after migration:

- `Plugin already registered under a different name: NAME=` (two installed distributions register one plugin module) → add `-p no:NAME`.
- Duplicate test basenames in directories without `__init__.py` (`import file mismatch`) → add `--import-mode=importlib`.
- pytest's capture file closed (`_pytest/capture.py ... I/O operation on closed file`, typically code that rewraps `sys.stdout` at import) → add `-s`.
- Known upstream renames in `PACKAGE_RENAMES` (for example `pinecone-client` → `pinecone`) → uninstall the old distribution and install the new one.
- Modules removed by a newer major release in `LEGACY_MODULE_PINS` (`langfuse.decorators` → `langfuse<3`, `pkg_resources` → `setuptools<81`) → install the pinned requirement. The pins are checked again after the LangChain/LlamaIndex legacy downgrades, which can surface them (old LlamaIndex imports `pkg_resources`).

The runner may also retry with LangChain capped below 1.0 when failure output indicates a pre-1.0 import path such as `langchain.vectorstores`, and with LlamaIndex 0.9 (all installed `llama-index*` distributions removed first, because the namespace layout cannot coexist with 0.9) when output shows a pre-0.10 import such as `cannot import name 'VectorStoreIndex' from 'llama_index' (unknown location)`.

Record every applied setup change under `setup_adjustments` in the before-migration result JSON.

## Node repository setup

For Node repositories without a root `package.json`, select a shallow nested Node project. Prefer a project that declares the target framework and has a test script.

Rank candidate projects by: a runnable `test` script first (its runner binary, such as `vitest` or `jest`, must be declared in the project or root dependencies; `node`, `bun`, and package-manager runners always count), then declaring the target framework, then being the root, then shallowness. A workspace root whose test script covers every package beats a package that only mentions the framework.

Use the package manager the repository declares (`bun.lock`, `pnpm-lock.yaml`/`pnpm-workspace.yaml`, `yarn.lock`, or `packageManager`), never a silent npm fallback when that tool is missing: npm on a pnpm/yarn project fails misleadingly (`workspace:*`, `only-allow pnpm`, ERESOLVE). Before any Node repository runs, `check_node_tools` logs the node/npm/pnpm/yarn/bun versions and paths (npm majors change install behavior, so results depend on them) and stops the run if node, npm, pnpm, or yarn is missing; a missing bun only fails bun projects.

The parent builds and packs the local Agent RT TypeScript package once per run (`build_agent_rt_npm_tarball`: `npm run build`, `npm pack`, then a check that `dist/index.js` and the compat entry points are in the tarball), and workers install that tarball (yarn as `agent-rt@file:<tgz>`). Installing the `typescript/` directory made results depend on its `dist/` at that moment and on each manager's local-directory handling, and migrated repositories failed to resolve `agent-rt/...`. A fresh checkout has no `typescript/node_modules`, so the builder first runs `npm ci` there when `tsc` is missing. If building or packing still fails, workers fall back to the directory only when it already has `dist/index.js`; otherwise the run stops with the build error, because a package without `dist/` makes every migrated TS/JS repository fail to resolve `agent-rt/...` and would be recorded as compatibility failures. The package builds run inside the main `try`, so a failure still stops the mock server and cleans the work root.

npm 12 stopped fetching lockfile tarball URLs (`allow-remote`) and git dependencies (`allow-git`) and running install scripts by default. `sanitized_env()` restores the npm <= 11 behavior (`NPM_CONFIG_ALLOW_REMOTE=all`, `NPM_CONFIG_ALLOW_GIT=all`, `NPM_CONFIG_DANGEROUSLY_ALLOW_ALL_SCRIPTS=true`; older npm ignores them) so results do not depend on the npm major; repository code is already untrusted and sandboxed.

Install dependencies from the nearest workspace root or lockfile directory at or above the selected project (`pnpm-workspace.yaml`, a lockfile, or a `package.json` with `workspaces`), because nested workspace packages have no lockfile and may use `workspace:` specifiers that only the root can resolve. Choose the package manager from that root (lockfile, `pnpm-workspace.yaml`, or `packageManager`). If the frozen install fails, retry once without a frozen lockfile, with `YARN_ENABLE_IMMUTABLE_INSTALLS=false` because `CI=1` makes Yarn Berry refuse lockfile changes (YN0028). If pnpm reports `ERR_PNPM_IGNORED_BUILDS`, retry with `--config.strict-dep-builds=false`. Bun projects (`bun.lock`/`bun.lockb` or `packageManager: bun@`) use `bun install`, `bun run test`, and `bun add --dev`. If npm corrupts its content cache mid-install (`EEXIST`/`ENOENT` renames under `_cacache`), clear the repository-local npm cache and rerun the same install. If npm reports a peer-dependency conflict (`ERESOLVE`), retry with `npm_config_legacy_peer_deps=true`, which stays set for later npm commands in that repository (including the Agent RT install). If the install fails in a pre/post-install lifecycle script (for example a preinstall that refuses direct package-manager use), retry once with `--ignore-scripts`. For a package inside a pnpm workspace, build its workspace dependencies best-effort (`pnpm --filter <name>^... run --if-present build`) before testing, because siblings are consumed from build output. Tests still run in the selected project directory. If initial tests fail because the generated Prisma client is missing (`Cannot find module '.../generated/prisma/...'`, `@prisma/client did not initialize yet`) and the repository installed the Prisma CLI, run `npx --no-install prisma generate` and retry; that command alone gets a dummy `DATABASE_URL` matching the schema's datasource provider when unset, because `prisma.config.ts` often resolves it just to load. If initial tests fail on missing build output (`Cannot find module '.../dist/...'`, `ERR_MODULE_NOT_FOUND` into `dist/`, `TS2307` for a scoped workspace package, or Vite's `Failed to resolve entry for package "..."` / `Failed to resolve import "@scope/..."`), build the workspace (`pnpm -r --if-present run build`, `npm run build --workspaces --if-present`, or the root `build` script) and retry. No detectable test command, or runner output such as "No tests found", records `NO_TESTS` rather than `SETUP_FAILED`/`FAIL`.

`sanitized_env()` allows dependency install/build scripts and remote/git dependencies for every package-manager version (`npm_config_dangerously_allow_all_scripts`, `npm_config_allow_remote=all`, `npm_config_allow_git=all`, and pnpm's `dangerouslyAllowAllBuilds` through `npm_config_` and `PNPM_CONFIG_`). npm 11.16+/12 and pnpm 10+ block them by default, which skipped Prisma/esbuild/native-module setup and refused mirror-registry tarball URLs, while npm 10 (which produced the existing results) ran them. pnpm 10.0–10.8 has no global switch, so for projects pinned to those versions `allow_legacy_pnpm_builds` sets `pnpm.neverBuiltDependencies: []` (dropping `onlyBuiltDependencies`/`ignoredBuiltDependencies`, which cannot be combined with it) in the install root's `package.json` before the baseline install, and records it in `setup_adjustments`. For pnpm 10.9+ (including 11/12) it only removes those allow-lists from `package.json` and `pnpm-workspace.yaml`: the environment switch conflicts with them (`ERR_PNPM_CONFIG_CONFLICT_BUILT_DEPENDENCIES`). This keeps results independent of the npm/pnpm version and depends on the required OS/container/VM sandbox, since repository scripts are untrusted.

Keep all package-manager caches repository-local to the disposable work root so concurrent workers cannot share mutable npm/yarn/pnpm state.

## Provider mocks

The migration-test tooling itself is pinned to CPython 3.13.13 through `.python-version`, `pyproject.toml`, and `uv.lock`; this is independent of the CPython 3.12 (default) used for tested repository's `.agent_rt_venv`. `@copilotkit/aimock@1.43.0` is pinned separately in `package-lock.json` because it is an npm package.

When work is pending, startup ensures the npm mock dependency is installed and starts one localhost aimock server shared by all workers. Inject deterministic dummy API keys only for providers whose SDK traffic is redirected to the mock (OpenAI, Anthropic, Google/Gemini, Groq, Cohere). Never pre-set keys for unredirected providers such as DeepSeek, Mistral, or OpenRouter: a key un-skips key-gated tests, which then call the real hosted API. Do not globally set base URLs for unredirected providers either; some test suites assert their default endpoints. Placeholders set a provider's base URL only together with its key. Redirect supported SDKs to the local mock server:

- OpenAI
- Groq, using the bare server URL because the SDK appends `/openai/v1`
- Anthropic
- Gemini through `google-genai` using `GOOGLE_GEMINI_BASE_URL`
- Ollama using `OLLAMA_HOST` / `OLLAMA_BASE_URL`
- Cohere using `CO_API_URL`

Disable LangSmith/LangChain tracing. `mock_server.mjs` supplies compatibility behavior that aimock does not currently provide, including the Gemini `models/*:batchEmbedContents` route and the current Ollama `/api/embed` response shape. Chat replies are structure-aware and deterministic: a `json_schema` response format gets the smallest instance that satisfies the schema (`schemaInstance`, following `$ref`/`$defs`, enums, `anyOf`, and minimums), JSON mode or a system/user prompt mentioning JSON gets `{}`, and anything else gets `mock response`. aimock omits the Responses API `usage.input_tokens_details`/`output_tokens_details` that the real API always returns (the OpenAI Agents SDK crashes on `None.cached_tokens`), so the `/v1/responses` pre-route adds them to non-streaming bodies and streamed `usage` objects. aimock also drops the Responses API `text.format`, so non-streaming structured `/v1/responses` calls are answered by a pre-route; other requests fall through to aimock with their body replayed (`replayBody`). The same mock serves baseline and migrated runs, so changing its replies requires rerunning both sides of affected rows.

## Migration rewrite rules

- Python rewrites preserve the upstream import path and prepend `agent_rt.`, touching only the roots in `PYTHON_IMPORT_ROOTS` (so `langchain_core` stays upstream). A bare `import pkg` becomes `import agent_rt.pkg as pkg` and `import pkg.sub` becomes `import agent_rt.pkg.sub; from agent_rt import pkg`, so the name the original statement bound still resolves.
- TypeScript/JavaScript rewrites preserve supported upstream package specifiers and prepend `agent-rt/`, but only when the result is a subpath the `agent-rt` package exports (read from `typescript/package.json` `exports`). Unexported specifiers such as `@langchain/core/*` or `@langchain/langgraph` stay on the upstream package, mirroring the Python root list.
- Mock targets move with the imports they stand in for, as a real migration would: TS `vi.mock` / `vitest.mock` / `jest.mock` (and `doMock`, `importActual`, ...) specifiers follow the same export-gated rule, and in Python, string module targets on lines using `sys.modules`, `patch(...)` / `patch.object` / `patch.dict`, `monkeypatch.setattr/delattr/setitem/delitem`, or string imports (`pytest.importorskip`, `importlib.import_module`, `__import__`) get the `agent_rt.` prefix. - AutoGen and CrewAI are Python-only Agent RT migration surfaces: they have no official TypeScript/JavaScript packages, so `repo_list.csv` carries no TS/JS rows for them. If one appears anyway, record it as unsupported rather than inventing aliases.

Keep rewrites narrowly scoped to the target framework import/package specifier. Do not turn this field test into a broad source-code migration engine.
