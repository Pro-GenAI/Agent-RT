Treat `README.md` as the source of truth for cross-framework comparison methodology, benchmark results, and reproduction documentation; keep maintenance and implementation rules in this `AGENTS.md`. Keep language-specific benchmark notes, runners, and measured data under `python/` and `typescript/`, generated comparison visuals under `assets/`, and comparison-only dependencies isolated from the main package environments (`python/.venv` for the comparison Python project and `typescript/node_modules` for the comparison TypeScript project).

Benchmark runs must be reproducible and scenario-specific. Avoid external model/API calls unless a benchmark explicitly requires them, prefer deterministic localhost mocks, run compared frameworks in isolated worker processes where runtime state could affect measurements, retain raw samples plus aggregates where applicable, and only publish measured results produced by the runners. Cold import/module-load benchmarks must remain provider-free and isolate every cold load in a fresh process.

Runtime comparisons must keep module load, first/subsequent construction, first/warm completion, first/warm streaming, conversation-length phases, warm loops, and concurrency phases separately observable. Long-conversation diagnostics must report incremental per-turn cost and stage memory; concurrency output must include p95 and throughput. Diagnostic-only modes, profiling, and filtered `--framework` runs must never refresh durable all-framework aggregates. Python profiling uses `cProfile`/tracemalloc; TypeScript profiling uses CPU profiles/heap snapshots. The Python localhost mock must retain enough listen backlog that 16-way concurrency is not server-queue-bound.

Unfiltered runtime runs with at least 30 successful samples may refresh the checked-in `python/runtime-measured-results.csv` or `typescript/runtime-measured-results.csv`; shorter or filtered runs must not. Tool/structured-output runners (`python/benchmark_features.py` and `typescript/benchmark-features.mjs`) must perform equivalent wire-level tool/schema work, keep validation semantics in the runner when framework-native schema libraries would make work unequal, record latency/CPU/raw samples plus post-timing memory, and only refresh `feature-measured-results.csv` from complete unfiltered runs with at least 30 samples.

Performance regression checks use `performance-baselines.json`. Keep checks report-only by default; strict mode may fail on configured regressions. Baseline updates must remain explicit, require at least 30 fresh successful runs for import/runtime inputs, and use percentage thresholds with absolute floors so small noisy metrics do not create routine false failures.

`promote_benchmark_baseline.py` is the resumable promotion path when a monolithic all-framework run exceeds orchestration limits. Filtered captures must never publish durable aggregates directly. Promotion must require every configured framework and at least 30 fresh runs per framework, preserve the benchmark runners' percentile semantics, recompute repeated runtime metrics from raw samples, fail closed on incomplete data, and write LF-only promoted CSVs.

Long-lived scalability diagnostics (`python/benchmark_scalability.py` and `typescript/benchmark-scalability.mjs`) must remain localhost/reproducible, run each framework in its own worker process, reuse one provider/client through each worker lifetime, measure both large sequential and bounded-concurrency phases, and record throughput, latency percentiles, process CPU, start/end/post-GC memory, sampled peak memory, and periodic memory samples. They must never overwrite durable benchmark aggregates. Keep worker safety limits enabled by default, record active resource-limit settings, and treat Linux-only resource-limit behavior as outside the cross-platform runtime guarantee.

Python second-phase diagnostics (`python/profile_import_dataclasses.py` and `python/benchmark_transport_coldstart.py`) are diagnostic-only and must never overwrite durable import/runtime aggregates or be presented as framework headline scores. The transport cold-start diagnostic must remain localhost-only and explicitly distinguish primitive HTTPCore feasibility from production proxy/TLS parity.

Tool-schema token comparison lives in `python/benchmark_tool_tokens.py`. Keep `tiktoken` isolated to the comparison Python environment, measure full-catalog main-model tool tokens separately from Agent RT Decision-model selection input, use the actual `make_decision_tool_visibility_filter` path with deterministic/no-network Decision-model doubles, and only refresh `python/tool-token-measured-results.csv` through the default-contract `--publish` path. Full-catalog results describe a benchmark configuration, not an inherent inability of alternative frameworks to filter tools.

Optional-integration dependency design and measured footprint evidence live in `optional-dependencies.md`. Keep optional integrations out of minimal installs, verify stripped core installs still work, and require actionable installation guidance when an optional integration is missing.

Comparison-only benchmarks, including tool-token benchmarks and scalability/resource-limit diagnostics, are not part of the package unit-test matrix. Any website or README benchmark claim must come from checked-in measurements here and include the relevant sample count, methodology/transport, and date/context rather than implying an overall framework score. Published benchmark updates must automatically regenerate the dependency-free SVG bar charts under `assets/` from durable CSVs: Python publication paths call `python/generate_charts.py`, TypeScript publication paths call `typescript/generate-charts.mjs`, and `README.md` should embed those generated charts rather than hand-maintained visuals.

Runtime benchmark implementation details: Python uses `python/benchmark_runtime.py` with `python/mock_llm_api.py`; TypeScript uses `typescript/benchmark-runtime.mjs` with `typescript/mock-llm-api.mjs`. Agent RT should exercise its production-default Responses WebSocket transport against the local `/v1/responses` WebSocket mock, including persistent connection reuse, `previous_response_id` continuation, and `stream_id` multiplexing, while alternative adapters may use their configured HTTP/SSE OpenAI-compatible paths. Keep each framework in a separate worker process. Measure module load, first/subsequent provider construction, first/warm completion, first/warm streaming, 5/20/100-turn conversations, a 100-request warm loop, and 1/4/16-way concurrent batches. Before warm completion and warm-stream samples, perform 10 untimed requests so startup/JIT effects are not mislabeled as steady-state latency. Preserve the legacy continuity fields `construction`, `completion`, `streaming`, `five_turn_loop`, and `concurrent_16_request_batch`.

Runtime memory staging must record RSS after module load, before/after provider construction, after first/warm completion, after first/warm streaming, after 5/20/100-turn phases, and after diagnostic cleanup/GC. `--diagnostic-turns N` must write separate diagnostic output such as `runtime-diagnostic-summary.csv` and never publish durable aggregates. Python `--profile` adds `cProfile` plus `tracemalloc`; TypeScript `--profile` adds CPU profiles, heap snapshots, and detailed `process.memoryUsage()` fields. Profiling is diagnostic only.

Feature benchmarks use the same localhost mock and must cover a two-request tool round trip with serialized JSON tool output, a five-round-trip tool loop, valid JSON Schema output, invalid-first structured output followed by repair, and 20 repeated requests with the same schema object. Keep validation in the benchmark runner so framework-specific Pydantic/Zod costs are not mixed into transport/adapter overhead. Write post-timing feature memory stages separately, currently under `results/features/feature-memory-stages.csv`.

Scalability diagnostics default to 5,000 sequential completions through one long-lived provider/client followed by 5,000 completions with bounded concurrency up to 256 in flight. Record median/p95/p99 latency, throughput, process CPU time/utilization, phase-start/end/post-GC memory, sampled peak memory, and periodic memory samples. TypeScript must also record V8 heap, external memory, and array-buffer usage. Keep default worker protection at 2 CPU cores and 1,024 MiB RSS unless intentionally changed; the parent must terminate workers that cross the memory cap. `--concurrent-calls` controls total work and `--concurrency` active in-flight work; `--max-cpu-cores`, `--max-memory-mib`, and explicit `--no-resource-limits` behavior must remain stable. Linux resource limiting must fail closed when required affinity/`/proc` support is unavailable unless limits are explicitly disabled.

For resumable promotion, filtered runtime captures may be written to separate output directories and promoted with `promote_benchmark_baseline.py`; filtered runs never publish directly. Import promotion pools `import-samples.csv`; runtime promotion pools raw scenario samples from `runtime-summary.json`. Recompute repeated runtime metrics from raw samples, pool cold/first metrics across chunk starts, use cross-chunk medians for RSS, preserve nearest-rank p95 semantics, require every configured framework and at least 30 fresh runs, write LF-only CSV, and fail before touching the destination when data is incomplete or malformed. Validate promotion logic with `uv run --project python --extra dev pytest -q comparison/test_promote_benchmark_baseline.py`.

Raw samples, stage-memory CSVs, profiles, and detailed CSV/JSON summaries belong under ignored `results/` directories. Performance regression checks use `performance-baselines.json`; support report mode, strict mode, and explicit baseline updates through `check_performance_regressions.py`. Baseline updates must reject import/runtime aggregates below 30 runs or import aggregates with failures. Keep threshold policy based on relative allowances plus absolute floors and continue covering cold load, first/warm construction, first/warm completion, stream first-text/total latency, five-turn latency, and runtime/stage RSS.

Future benchmark classes should use equivalent logical work, deterministic local responses where possible, isolated environments, repeated measurements, and retained raw per-run samples. Planned or expanded classes may include tool loops, structured-output behavior, and deployment footprint; keep roadmap/implementation planning here rather than in the user-facing comparison README.
